# 生产数据保全与迁移验收方案

状态：准备方案，未在生产执行。
当前风险依据：Render免费服务、本地SQLite路径代码、COS配置说明及共享表覆盖；不是假定用户数据已丢失。

## 数据归属

SQLite是当前本地主库，持仓等部分业务数据可同步到PostgreSQL；代码存在COS快照机制，但用户说明未在Render配置COS。
20张表的名称、字段与覆盖见SCHEMA_AND_BACKUP_COVERAGE.md；行情/EV等缓存虽可重算，其历史来源与复权追溯不能从无元数据的缓存自动恢复。
保全目标首先是完整一致性副本，再决定哪些表可在新架构重建。不得先清库或仅导出持仓CSV后就认定完成全量备份。

## SQLite验收步骤

1. 明确真实路径和最后一次业务使用时间；不运行会触发同步/扫描的app.py来查看。
2. 在来源可读且授权范围满足时使用SQLite一致性备份机制取得完整副本；WAL开启时不能只复制主.db文件。
3. 下载/保存于D盘受控备份目录；文件名含UTC取得时刻，记录SHA256、大小、SQLite版本与schema摘要。
4. 对副本执行integrity_check、20表存在与行数、主键/关联一致性抽样；区分真实空库与备份失败。
5. 再复制到隔离恢复库，用关闭网络/自动任务的既有应用核对持仓、Forward、研究任务、交易和候选策略；只报告计数或匿名摘要。
6. 原始快照保留；恢复验收库不覆盖来源、不连接共享生产库、不上传备份到GitHub。

## PostgreSQL验收步骤

先确认应用实际连接这个实例，以及11表哪些是权威记录。到期前取得可恢复逻辑副本，记录schema/行数。
外连受限时优先用现有获准的内部/只读连接；不可在审计期间改IP允许列表。
恢复到隔离PostgreSQL并核对表、主键、时间字段和数量；SQLite同步11表并不替代PostgreSQL完整备份，也不覆盖SQLite其他9表。
恢复和持久化资源创建若需线上变更，另行明确授权，当前不执行。

## 持久化方案的选择条件

现有免费Web服务无法把本地SQLite视为长期主存储。后续可比较：持久数据库为权威存储，或付费服务持久磁盘承载SQLite并配异地备份，或可靠D盘计算端加受控同步/云备份。
方案必须说明权威库、缓存、同步冲突/删除、备份范围、恢复目标、费用和运行责任；不因审计发现风险自动购买/升级。
COS快照是备份途径，不自动解决多端权威库、未备份窗口或后台任务可靠性。

## 切换和回退

先完成真实备份恢复，再在副本迁移与对账。采用小范围影子读取验证后才考虑正式切换。
上线前冻结schema/代码版本与回退条件。回退不仅是git回到旧提交：必须保持数据schema兼容及新写入记录可恢复，不能丢弃迁移后业务记录。
未验收上述条件时只允许D盘隔离开发，不部署新数据路径。
